## 按 sdkwork-specs 规范处理后端集成（同源 API 边 + 后端代理）

**规范依据**（APP_SDK_INTEGRATION_SPEC §5）：浏览器 SDK 客户端必须配置**保留规范路径的 API 边**（同源 base URL），代理路由到「显式依赖上游」发生在 API 边后面。当前 PC 直连 `:3900` 不符合规范且导致 404。

### 1. 同源化 runtime-env（前端）
- `apps/sdkwork-webserver-pc/etc/browser/runtime-env.{development,test}.json`：`deployAppApiBaseUrl` 改为 `"/"`（standalone.production 已是 `"/"`；cloud.* 保持绝对 URL）
- `scripts/materialize-runtime-env.mjs`：`deployAppApiBaseUrl` 加入 `SDK_BASE_URL_KEYS`（standalone 强制 `/`，强化规范约束）
- `packages/sdkwork-webserver-pc-core` 已支持 `"/"`→origin 解析，`DeployDomainManagementSurface`/surfaces 接线无需改

### 2. vite dev 多目标代理（dev 体验）
- `specs/topology.spec.json`（webserver 根）：新增 deploy API surface/envKey（参照 `platform.api-gateway` 模式）
- `etc/topology/standalone.development.env`：`SDKWORK_WEB_DEPLOY_APP_API_BASE_URL=http://127.0.0.1:3900`（cloud.*.env 同步网关 URL）
- `apps/sdkwork-webserver-pc/scripts/browser-topology.mjs`：`proxyTarget` 结构化（default=ingress :3800，deploy=:3900）；`createCanonicalApiProxyConfig` 支持双目标——`/app/v3/api/domain_zones`、`/app/v3/api/certificates` 具体前缀排前指向 deploy，其余 canonical 路径指向 default（无 rewrite，规范路径原样透传）
- `vite.config.ts`、`browser-topology.d.mts`、`tests/vite-topology-config.test.mjs` 同步适配

### 3. webserver 后端代理（核心后端集成，新 crate `sdkwork-routes-webserver-deploy-app-proxy`）
- 路由：`/app/v3/api/domain_zones`（精确）+ `/{*rest}`、`/app/v3/api/certificates` + `/{*rest}` → **reqwest 原样转发**到 deploy 后端（method/path/query/body + 头透传：access-token、auth-token、x-api-key、idempotency-key、correlation 头，剔除 hop-by-hop；回写状态/头/体；upstream 不可达 → 502）
- 配置：`SDKWORK_WEB_DEPLOY_APP_API_BASE_URL`（`ProviderSdkConfig::from_env` 风格校验：prod 强制 https、dev 允许 localhost）
- 装配：`sdkwork-api-web-server-assembly/src/bootstrap.rs` 与 `mount_app` 并列 merge（standalone 门控内）；**无需 manifest 条目**（已确认 `ManifestAuthorizationPolicy` 对未知路径仅要求已认证，权限校验由 deploy 端负责；dev DevInline 无权限门槛）
- 测试：tower oneshot + 内嵌 axum fake upstream，断言路径拼接、dual-token 头透传、响应回写、upstream 不可达 502（仿 `tests/app_web_framework_routes.rs` 模式）

### 4. webserver app-api certificates 让位（解决同源路径冲突）
`/app/v3/api/certificates` 前缀被两个后端占用，同源 API 边下只能有一个所有者（证书归 deploy = 迁移方向）：
- `crates/sdkwork-routes-webserver-app-api/src/routes.rs`：移除 certificates 路由注册（list/issue/operations）；`sites/.../listener_certificate_bindings` 保留（路径不同无冲突）
- `apis/app-api/web/openapi.yaml`：移除 `/certificates`、`/certificates/issue`、`/certificates/operations/{id}` 路径 → `pnpm api:materialize` 再生成 JSON 契约、路由 manifest、web-app-sdk（webserver PC 已无证书调用，消费方零影响）

### 5. 验证
- `cargo test`（新代理 crate + assembly + routes）
- webserver PC `pnpm test`（vite-topology / materialize-runtime-env / console-workspace 适配）+ `pnpm typecheck` + `vite build`
- 手动链路：启动 deploy 后端（:3900）+ webserver 后端（:3800）→ `curl :3800/app/v3/api/domain_zones` 验证转发；PC dev（:5182）Domains 页同源请求经 vite 代理到 deploy

### 风险与说明
- **生产环境权限**：deploy 端按自身 manifest 校验 `deploy.domainZones.*`/`deploy.certificates.*`——生产用户 scope 需含相应权限（dev DevInline 无碍）
- **deploy 后端需启动**（`cd sdkwork-deployments && pnpm dev`，:3900）——webserver dev 不再依赖它也能启动，但 Domains 页功能需要它
- webserver `backend-api` 证书面（/backend/v3/api/certificates）与 `web_certificate_*` 表本轮不动（Phase 3 下线）
- 涉及 webserver 仓库：前端 6 文件、后端新 crate + 装配 + app-api routes、OpenAPI+生成物、拓扑/环境变量 3 文件、测试 3 个
