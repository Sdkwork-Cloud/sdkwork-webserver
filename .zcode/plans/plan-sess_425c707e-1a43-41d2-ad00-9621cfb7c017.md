## Phase 1 统一资源模型：一份启动配置混合 本地/Drive/知识库 三种部署方式

### 目标
扩展 `sdkwork.webserver.config.json` 的 `resources[]`，新增 `drive` 和 `knowledgebase` 两种资源类型，使一份配置可混合：本地 static/proxy/redirect/respond + Drive space（或子目录）+ 知识库 wiki，按 vhost/route 分流。云模式（website runtime-set executor）行为不变。

### 现状锚点（已探查确认）
- `ResourceConfig` 是 `tag="type"` 的 kebab-case 枚举（core `config/model.rs:762-809`），只有 Static/Proxy/Redirect/Respond；schema oneOf 在 `specs/sdkwork.webserver.config.schema.json:60-80`
- handler 分派在 `data_plane/handler.rs:245-325` 的 `match selected.resource`；provider traits/registry/executor 全部可复用（`WebsiteStaticContentProvider`/`WebsiteWikiProvider`/`WebsiteProviderRegistry`/resolution cache）
- resolution cache 是 `pub(crate)`——因此在 delivery-runtime 内部新增执行器组件，零可见性改动
- core 不依赖 contract/delivery-runtime（依赖方向相反），分层天然干净：core 管配置契约，gateway 管装配执行

### 实施步骤

**1. 配置契约（core crate）**
- `specs/sdkwork.webserver.config.schema.json`：resources oneOf 追加 `$defs/driveResource`、`$defs/knowledgebaseResource`
  - drive：`id` + `providerResourceUuid`（1..128，无控制字符）+ `resourceSubpath`（可选，安全相对路径，允许嵌套）+ `indexFiles`（默认 `["index.html"]`，单段约束同 static）+ `spaFallback`（可选，单段）+ `cache`（可选 `{metadataTtlSeconds, negativeTtlSeconds, staleWhileRevalidateSeconds}`，TTL 上限对齐 descriptor deliveryPolicy 约束）
  - knowledgebase：`id` + `providerResourceUuid` + `locale`（可选，≤35 字母数字+`-`）+ `cache`（可选）；**禁止** indexFiles/spaFallback（对齐 WIKI mount 语义）
- `config/model.rs`：`ResourceConfig` 增加 `Drive`/`Knowledgebase` variant + `id()` match 同步；新增 `ProviderCachePolicy` 结构
- `config/validate.rs`：新 variant 校验——subpath/indexFiles/spaFallback 走现有 `validate_relative_path`；KB 拒绝 index/spa；providerResourceUuid/locale/cache TTL 边界；resource 引用有效性
- `config/compiled.rs`：新增 `provider_resources()` 访问器（返回配置中所有 drive/kb resource 引用列表，供启动装配与 reload 校验）；compile 阶段不做远端检查（保持纯本地）
- `config/model.rs` limits：新增 `providerTimeoutMs`（默认 30000，对齐云模式 provider timeout）
- `tests/webserver_config.rs`：新增 schema/语义测试（合法 drive/kb、subpath 逃逸拒绝、KB 带 index 拒绝、locale 非法、cache TTL 越界）

**2. 执行器（delivery-runtime crate）**
- 新增 `resource_executor.rs`：`AppConfigResourceExecutor`
  - 持有 `Arc<WebsiteProviderRegistry>` + resolution cache（内部使用，零可见性改动）+ buffered content admission
  - `execute_static(...)`：候选链（目录→indexFiles→spaFallback）→ resolve（走 cache）→ open → 产出复用 `WebsiteDeliveryOutcome`；404 语义与 executor.rs 一致（NotFound/NotPublic/Revoked 透传）
  - `execute_wiki(...)`：resolve_wiki_route → Content/Redirect/NotModified → open
  - 内部 deadline 用 tokio timeout（`providerTimeoutMs`）
- `registry.rs`：新增 pub `validate_provider_resource(...)`（把现有 set 级校验的 job 逻辑提取为单资源校验，供启动时 fail-closed 验证）

**3. 装配与执行（gateway crate）**
- `website.rs`：复用 `build_drive_provider`/`build_knowledgebase_provider`，新增 `build_app_config_provider_executor(config)`：收集配置引用的 provider 类型 → 无引用返回 None（不引入 env 依赖）→ 有引用则从 env 装配（base URL+token 成对、`SDKWORK_WEB_WEBSITE_TENANT_SCOPE_HASH` 必需、staging/production 强制 https）→ 对每个引用资源 `validate_provider_resource`（purpose=Activation，失败即启动失败）→ 构造 executor（buffered 256MiB/cache 16K，沿用现有 env 覆盖）
- `watch.rs`：`run_data_plane_from_config_with_operations_until` 装配 executor 并注入 runtime；reload 候选若引用未装配的 provider 类型 → 拒绝（保留 last-known-good）
- `handler.rs`：match 增加 Drive/Knowledgebase 分支 → 构造 `WebsiteDeliveryRequest`（复用 website_delivery.rs 的 request_id/trace_id/conditions/range/client 分类模式）→ 调 executor → 响应组装（200/206/304/404/405/416/429/502/503 + ETag/Last-Modified/Accept-Ranges/Cache-Control/X-Request-Id/Vary/nosniff/Referrer-Policy；HEAD 抑制 body；GET/HEAD only + 405 ALLOW）
- 路径翻译：Drive = route strip 前缀（复用 static 语义）→ `"/" + resourceSubpath + relative` 规范化；KB = 请求路径直接作为 wiki route

**4. 示例与文档**
- 新增 `etc/examples/sdkwork.webserver.config.mixed.json`：同一配置混合 local static + proxy + drive space 挂载 + 知识库 wiki
- `docs/architecture/tech/TECH_ARCHITECTURE.md` 配置所有权小节更新

**5. 验证**
- `cargo test -p sdkwork-webserver-core`、`-p sdkwork-webserver-delivery-runtime`、`-p sdkwork-api-web-server-standalone-gateway`
- `cargo fmt --check`；`gateway validate` 对混合示例配置人工验证

### 明确不在本次范围（后续阶段）
- 云模式 executor 与 select_route 共存（404 回落）——更大的架构改动，保持云链路不动
- provider 凭据轮换、多租户节点、body 真流式、本地模式事件失效接线（Phase 3）
